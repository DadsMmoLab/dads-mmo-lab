# Changelog

Every release of Yu'lon, newest first. The **Unreleased** section is titled by the lead when a release is cut; until then it collects what has landed on the working branch since the last tag. Entries say what a player or operator can now do, and how it was proved on a real machine. The raw gate captures behind them are kept in the maintainers' local notes rather than in this repository, because they name our own machines and accounts; an entry says what was run and what it showed.

## Unreleased
- A mob multiplier outside 0.01 to 100 is refused before anything runs. Baby, Nerf, Buff and Extreme Buff Mobs multiply creature health, damage, armour and attack time by what you type, and their Remove divides it back; at 0 the install wiped every creature's value and Remove could not divide it back (MySQL writes NULL for a division by zero), a negative number flipped the sign, and a tiny or huge one does the same damage more quietly (the modifiers are single-precision numbers, so ×1e-50 rounds to 0 and ×1e39 overflows). Each of their four questions now takes 0.01 to 100, ends included: the dialog keeps OK greyed out with "this must be between 0.01 and 100" under the box, on Install and on Remove, an answer remembered from an earlier build is not pre-filled if it is out of range, and the install code refuses it on its own, along with non-numbers such as `inf`, for anything that hands it values without the dialog, before a single statement is sent. 0.25 and every other multiplier in the range install as before. The range is a pair of new `min`/`max` fields on a number question in the manifest format, so no other question changed; 0.01 and 100 are a ruling, since nothing upstream names a range. Proved by tests on the real dialog and the real install code, and live on a WotLK test server with only its database running, through the Modules tab's own action code (driven from a script): a 0 left OK greyed out, the install code refused it when called directly, and the creature table was untouched (T122, `t122-reject-zero-multiplier-*`)
- Running Baby, Nerf, Buff or Extreme Buff Mobs again no longer stacks its multipliers. Each of the four multiplies creature health, damage, armour and attack time relative to what the database already holds, and pressing Install again (their row keeps reading Not installed, because they leave no folder behind) multiplied again: installed at ×2 and then at ×3, creatures ended at ×6, and Remove then took them back only to ×2. Yu'lon now records the multipliers it applied, beside your saved answers. A second Install first divides by those and then applies the new ones, in one database transaction, so creatures land on base × the new values (attack times are whole numbers, so after a fractional multiplier one can end 1 ms off); Remove divides by what was applied and then forgets it. Yu'lon marks the record just before it sends the SQL and settles it after the commit, so if the app is closed or killed in between, or the database connection fails so that Yu'lon cannot tell whether the change landed (it says so), the next Install refuses and Remove asks which values are in the database, rather than trusting a record that may be wrong. Where Yu'lon has no record that one is applied — an install by an older version, or one already removed — Remove asks for the values, filled in with your last answers, and says it may not be applied at all, instead of silently dividing again. A record Yu'lon cannot use (damaged, or a multiplier of 0, which nothing can divide back) refuses a second Install with "Remove it first, then Install" before any question is asked. The second Install's dialog now says the new values replace the old ones. An install made by an older Yu'lon leaves no record and cannot be told apart, so installing over one of those still stacks. Proved live on a WotLK test server through the Modules tab's own action code (driven from a script, not by clicking), database only: Baby Mobs installed at ×2 doubled every sampled creature's values, installed again at ×4 read ×4 (not ×8) with the new note in its dialog, and Remove asked nothing and put the whole creature table back bit for bit (T115, `t115-mob-multiplier-rerun-*`)
- Every module question is asked now, and Yu'lon remembers your answers. Before, the Modules tab opened its question dialog only for a question with no default (and, since the Hearthstone fix below, a choice), so every other answer was the catalog's default whether you wanted it or not: Bigger Stacks on Tortoise, Vanilla and TBC was always 200, the XP rates and the message of the day always the catalog's, the Baby, Nerf, Buff and Extreme Buff Mobs multipliers always theirs. Install and Update now open one dialog per module with every question it uses, already filled in, so accepting is one click — for Accountwide Systems that is all thirteen of its sharing switches, in one dialog whose questions scroll when the window is small (proved at the 960×640 minimum by test), each showing No as the catalog says (a yes/no default written as a word used to leave its box reading Yes). What you answer is kept for that server install, so the next Update or re-install opens on your last answers instead of the defaults, and a module's settings re-applied without new answers use your saved ones before the catalog's — Hearthstone Tweaks installed at 5 minutes stays at 5 minutes when you Update and press OK, where it used to go back to 30. Removing a Baby, Nerf, Buff or Extreme Buff Mobs tweak undoes it with the multipliers saved at install and asks nothing; where none are saved — an install made before this, or a damaged record — Remove asks for them, filled in with the defaults, and says that any other value leaves the creatures multiplied, rather than silently dividing by the default. Running one of those four again no longer stacks its multipliers on top of the last ones (the mob multiplier fix below). An install made before this has no saved answers: its Update dialog shows the defaults and says so. A saved-answers file Yu'lon cannot read is left untouched rather than overwritten. Four questions that never did anything are gone or now work: NPC Teleporter's Onyxia level (60 or 80) is now written into the one portal row upstream sets from it; its "install the capital / starting-zone NPC" questions are gone (both NPCs are always installed, as before); Portals in All Capitals no longer asks for id ranges it never used; WotLK's All Stackables to 200 no longer asks for a size (upstream ships only 200). Accountwide Systems no longer loads both of upstream's reputation scripts at once — only the stock AzerothCore one runs, and the variant made for another server's modified faction data is renamed to `.lua.unused`, an extension the Lua engine's loader does not accept (read in mod-ale's own source at the commit our WotLK server builds; the rename and the Remove of either name are proved by unit test, not by a running world); an existing install is fixed by its next Update, and Remove now deletes that script under either name. The stock reputation script is installed as `AccountReputation.lua`, the file its on/off switch is written into: since installs began applying those switches, every Accountwide Systems install had stopped with "patch target missing: …AccountReputation.lua", because upstream ships no file by that name (found and measured against the real upstream repository while merging; all thirteen switches now land). Proved live on a WotLK test server through the real Modules tab: Hearthstone Tweaks installed at 5 minutes landed on the Hearthstone item (300000 ms), an Update from a freshly opened window offered 5 minutes with the "your answers from last time" line and OK kept 300000, XP Rate Customization's three multipliers — never asked before — opened pre-filled with 1 and Cancel changed nothing, and Remove put the cooldown back to stock without asking (T104, `t104-ask-all-remember-*`)
- The random-bot count you set now survives a Repair, Update to latest, switching the command channel on or off, and the install's conf step being run again. Each of these rewrote the file that holds the count, and put the install's 500 back in it: `docker-compose.override.yml` on WotLK, `etc/aiplayerbot.conf` on TBC, Vanilla and Tortoise. They now read the lowest and highest number out of the file they are replacing and write that pair again. When there is no file, it cannot be read, or its numbers are not two whole numbers with the lowest not above the highest, the install's 500 is used as before. Nothing is asked of the machine to decide this. A pair left in `aiplayerbot.conf` by an install that stopped before its conf step finished is the image's template, not a choice, so it is not carried. Switching the channel off also keeps a number that was changed while it was on. Reset to default still puts 500 back, on purpose. This also means an install nobody changed keeps its 500 as if it had been chosen, so if a later Yu'lon release changes the installed number, existing installs do not pick it up through a Repair or an update; Reset to default does. Proved on yulon-ubuntu on a real WotLK install with its channel on. The bots were set to 60 through the Bots box's own code, then a Repair was run through the install's own `run()`. Afterwards the override still said 60, the recreated world's environment said 60, and the database had 60 bots online, with SOAP still answering. The channel was then switched off and on again through the Server tab's code. The count stayed 60 both times, and the override after switching it off was the pre-channel file with only the two bot lines changed. The TBC, Vanilla and Tortoise side was proved by tests only, which run the install's conf step again over a file set to 60; there was no CMaNGOS install on the box. (T117, `t117-keep-bot-count-*`)
- Saving a card on the Tuning tab no longer makes a private settings file readable by everyone on the machine. The save wrote the new file at the system's default permissions, so a TBC, Vanilla or Tortoise `.conf` that the install keeps owner-only came back world-readable — for `mangosd.conf`, which a module card such as the XP rates reaches, that exposed the database password to every local account. The file now keeps its own permissions, and the new text is owner-only while it is written, the way Reset to default already writes. Proved by a test that saves a 0600 file with the usual 022 umask and finds it still 0600. (T116, `t99-bot-count-*`)
- The number of random bots can be changed. The Bots tab now has a **Random bots** box on all four games: it shows the number the server is set to, read from the install's own settings, and **Apply…** sets both the lowest and the highest number of bots to it, as the install's 500 does. On TBC, Vanilla and Tortoise it writes `AiPlayerbot.MinRandomBots` and `MaxRandomBots` in `etc/aiplayerbot.conf`; on WotLK it changes the values of the two `AC_AI_PLAYERBOT_*_RANDOM_BOTS` lines in `docker-compose.override.yml`, which is where WotLK's bot count really lives, and nothing else in that file — lines added by hand, `:z` bind labels and the command channel's settings stay exactly as they were; if either line is missing or there twice, it says so and writes nothing. Each file is backed up beside itself first, and the running server keeps its bots until it is restarted (TBC, Vanilla, Tortoise) or its containers are recreated (WotLK); the Bots tab and the Tuning tab both offer that button when the change is written. The box goes from 0 to what the server can actually reach: on TBC and Vanilla that is 9 bot characters per bot account, 900 on a standard install, and the tooltip says how to raise it (an account count of 0 or not a number gives no limit rather than a box stuck at 0). On Tortoise and WotLK the settings set no limit, and a number above 500 is warned to cost memory and processor time. On TBC, Vanilla and Tortoise the Tuning tab also shows the bot settings Yu'lon writes into `aiplayerbot.conf` as a **Playerbots (server settings)** card. A change to a CMaNGOS game's own `etc/` files is now priced as a restart everywhere, since the containers read that folder from disk; that includes a Reset to default. Only Reset to default puts the number back to the install's 500, on purpose, and the box then shows 500 again. Proved live on m910q through the real Bots tab. On a TBC install, 500 → 50, **Restart server…** from the Bots tab, and the world reported `Playerbots: 50 online` with 50 bot characters online in the database out of a pool of 900. Then back to 500, restart, and 500 online four minutes later. On a WotLK install, 500 → 60 and **Recreate containers…**: the new container carried `AC_AI_PLAYERBOT_MAX_RANDOM_BOTS=60`, and the world reported 60 characters in world, 60 of them bots. Back to 500 and 500 online. Only those two override lines changed each time, and the file kept its mode; a re-check after the review did the same on an override carrying a hand-added line, which was still there after Apply and the recreate. (T99, `t99-bot-count-*`)
- A server's own settings can be put back to how Yu'lon installed it. **Reset to default ▾** on the Tuning tab offers **All server settings…** and one entry per settings file of that game (`mangosd.conf`, `realmd.conf`, `aiplayerbot.conf` and `ahbot.conf` on TBC and Vanilla; `aiplayerbot.conf`, `modules/tortoise_bots.conf`, `mangosd.conf` and `realmd.conf` on Tortoise; `worldserver.conf`, `authserver.conf`, `modules/playerbots.conf` and `docker-compose.override.yml` on WotLK). "Default" means what a fresh install writes, not the bare upstream file: on the three CMaNGOS games the image's own template with the install's database logins, world port, command channel, 500-bot population and auction-house settings put back in; on WotLK the compose override is made again exactly as the install makes it — bot population included, and the command channel kept if it was switched on — so a hand edit that stopped the server from letting anyone log in is undone, and the tab then asks for a container recreate, which an environment change needs. Every file is made first and nothing is written unless all of them could be; each file is backed up beside itself (`<file>.<time>.reset-<id>.bak`, one id per press), a core file that was deleted is made again as the install makes it, and **Undo the last reset…** puts them back — also after Yu'lon was closed or stopped half-way, because it reads the last reset off those backups — backing each file up again first, so nothing tuned since is lost. Module files are kept, and so is every setting an installed module keeps inside one of these files (XP rates, for example): only the server's own settings go back. It works while the server runs; the tab then offers the restart or recreate the files need. Proved live on m910q through the real Tuning tab. On a TBC install with its bot count, world port, command channel and realm login edited by hand, **All server settings…** gave back all four files byte for byte as the install had written them, with the database logins intact. After the recreate the tab offered, the world came up and answered `server info` over SOAP. On a WotLK install whose compose override had been broken by a mis-indented timezone line, which stopped `docker compose` from even reading the stack, the reset made the override again byte for byte as installed, with 500 bots. The recreated world came up, answered on its console, and the login server answered the client's first message. **Undo the last reset…** put every hand edit back byte for byte, in the same session and after the app was restarted. Closing the window during a reset was refused until it finished. (T94, `t94-reset-settings-*`)
- A Repair keeps the command channel on. Running Install again over a finished WotLK install (a Repair), and Update to latest's put-back of the compose files, both rewrite `docker-compose.override.yml`, and they wrote it without the channel's SOAP settings. So when the channel had been switched on, the Repair's own start brought the world up with SOAP off, while the Server tab still showed the channel as working. A Roll back pressed after that only released the port. It left the file alone and kept its backup, so the install still read as channel-on. The override is now rewritten with the channel's settings whenever the channel is on, the same way the Tuning tab's reset already did, so Roll back afterwards puts the installed file back. An install whose channel was rolled back reads as off even when the rollback had to keep its backup, so a later Repair does not switch SOAP back on. Proved on yulon-ubuntu on a real WotLK install with its channel on. Before the fix, a Repair wrote the pre-channel override back byte for byte, the recreated world had no `AC_SOAP_ENABLED`, `server info` over SOAP found nothing listening, and Roll back left the file and its backup in place. With the fix, the same Repair left the override byte for byte as the Enable press wrote it, and the recreated world answered `server info` over SOAP. Roll back then restored the installed override byte for byte, removed the backup and released the port. (T101, `t101-repair-keeps-channel-*`)
- An existing Tortoise, Vanilla or TBC server can now take the compose fixes made since it was installed, when you choose. Nothing rewrote those servers' `docker-compose.yml` after the install, so the shutdown protection above reached new installs only. When the Server tab sees that the file differs from what this version of Yu'lon writes for that server (another version wrote it, or it was edited by hand), an amber banner offers **Repair server files…**. A reworded comment is not a difference. A file you took over, one whose folder was moved after the install, and one whose folders are labelled for SELinux on some lines and not others are never offered. The press asks first and says how many lines it adds and removes. Yes backs the file up beside itself as `docker-compose.yml.<date>.repair.bak`, then writes the file again the way this version installs it, keeping its mode, this server's own project name and the SELinux `:z` labels the install gave it (read from the file, not from the host). If the file changes between the check and the write, the write is abandoned and the file left as it is. It changes nothing else: not the override, the build file, `.env`, the `.conf` files or the characters. The banner then offers the **Recreate containers…** that puts the running server on the new file, and the Tuning tab lists the same recreate. WotLK is not offered it, because its compose file already follows the app at *Update the server to latest…*. Proved on m910q on a TBC server installed before T98, whose file was byte for byte the current render without T98's database block. With the world up, the banner showed; the repair wrote exactly the new render (62 lines added, none removed) and a backup identical to the old file, and left the override, build file and `.env` untouched. The recreate brought the world back (`World initialized` 70 s later) on a database container that now has the shutdown hold and the 5-minute grace. `docker stop` of the world, login server and database together then showed the database holding (`holding shutdown, 10 server connection(s)`) and shutting down cleanly 0.9 s after the world had exited. (T106, `t106-repair-server-files-*`)
- A server can be removed from Yu'lon without deleting anything. Hover its tab in the sidebar (or look at the selected one) and press the ×, or right-click the tab → "Remove from Yu'lon…". One warning, defaulting to No, says what goes (the tab and Yu'lon's record of it), what stays (the folder, the database volume with the characters, the images), that a running server is stopped first, and how to bring it back: "Use existing…" on its Catalog tile, pointed at the same folder ("Find in WSL…" for a server in a WSL distro), which brings a removed server back as it was. A tab with a job running (a rebuild or database update, a module install, a backup or restore, a network change, another Server action) refuses and names the job. A stop that fails asks once more before letting go of a server that may still be running, and a world still loading can take a few minutes to stop (it ignores the stop until it has loaded), which the Server tab now says while it waits. Every game's Server tab now always carries a small "Remove from Yu'lon…" button that opens the same dialog, so a gamepad or a Steam Deck reaches it too. The button lights up when it is the way out: the server's folder is gone, or "Stop and remove containers…" found nothing to remove, and that message now names it; Uninstall's refusal for a folder Yu'lon did not install points at it as well, instead of at the retired "Forget this install…". TBC and Tortoise had no way off the list at all before this, so an adopted Tortoise server whose containers were deleted by hand was a dead end: every press of "Stop and remove containers…" ended "no containers to remove". Its status line now says the world container does not exist instead of "docker did not answer". Reported on Discord 2026-09-22/23. Unit-proven on Python 3.11 and 3.13. Proved on m910q through the real window, with a real pointer on a private X display: the × showed on the hovered tab and on the selected one, never on Catalog, and stayed under the pointer; pressed on a running TBC server and answered Yes, it stopped the server first and only then dropped the tab and its `state.json` row, keeping the folder, the containers, the database volume and the image; No left everything as it was; a Start and a backup in progress each refused and named the job; the right-click entry removed a server. On a copy whose containers were gone, every press of "Stop and remove containers…" said there was nothing to remove and lit up "Remove from Yu'lon…", the status line said the world container does not exist (and still "docker did not answer" with Docker unreachable), and the button took it off the list. "Use existing…" brought the TBC server back, and it started and stopped. (T95, `t95-forget-x-*`)
- Turning the command channel on keeps a Fedora server's SELinux labels. On an enforcing host the install puts `:z` on every host bind, and the Enable press rewrote the compose override without it, so the world's `./modules` bind lost its label: the server still started while the folder kept the label the install had given it, and once the folder lost that label (a `restorecon` of the home directory does it) the worldserver crash-looped on `Permission denied` under `/azerothcore/modules`. The press now renders the override with the same label the install uses, and a rollback recognises the channel it wrote whether that file carries the label or was written by an older version without it, and whatever the host reports at rollback time (SELinux since switched to permissive, or a probe that cannot tell), so the channel no longer sticks on. Proved on `yulon-fedora` (Fedora 44, Enforcing) on a WotLK install run from re-tagged images (compose files and relabel written by the app, images re-tagged from the box's existing build of the same tree, not compiled for this run): before the fix the press dropped `:z` and the unlabelled world looped eleven times; after it the override kept `:z`, the same unlabelled folder was relabelled at Start, the world came up, the channel's account was made and SOAP answered from the host, and a Start with 7878 held rolled the override back byte for byte to the installed one, removed its backup and released the port. (T102, `t102-channel-selinux-*`)
- Repairing a finished WoW WotLK install — installing it again into the folder that already holds it — is no longer refused for the room its build already used. It was refused before the first step with "28 GB free, and the install needs 48 GB": Docker's 40 GB for the build plus the folder's 8 GB, on a drive where the build was long done. The T112 fix below, for installing into an existing folder, covers WotLK too, because WotLK's installer uses the same free-space check; it is now held to it by tests of its own, with WotLK's numbers, so the build's share is dropped only when the folder's record says the build is done and Docker still holds all four images it makes (world, login, database import and server data), and a drive below the folder's own 8 GB is still refused even when every step is recorded done. 8 GB covers what a Repair can still write after the build on the box it was proved on: the server-data volume there holds 3.2 GB (its download is about 1.1 GB more while it unpacks) and the database 1.8 GB. Proved on m910q with the disk as it was, 17 GB free: the Repair of a finished WotLK install went past the check, skipped the compile, found its server data and databases in place, and brought the world up in 100 seconds (T114, `t114-wotlk-repair-preflight-*`)
- Installing a game into the folder that already holds it is no longer refused for the room its build already used. The free-space check ran before anything looked at the folder's install record, so it asked a finished WoW TBC install for a fresh install's 40 GB — the build's 20 GB plus the folder's 20 GB — and a box with 21 GB free was refused after one second. It now asks the install what it will actually do: when the record says the build is done and Docker still holds every image it made (the same test the build uses to skip the compile), the build's share is not asked for again, and the rest is still judged against the server folder's own floor — a drive below that is refused even when every stage is recorded done, because a stage that finds its maps or data gone writes them again. A fresh install, a resume that has not reached the build, and a recorded build whose images are gone are asked for the whole floor exactly as before. Proved on m910q: the same press through the real window into the same TBC folder, 21 GB free, went past the check, resumed without compiling and brought the server up (T112, `t112-preflight-resume-*`)
- Closing Yu'lon while something is stuck no longer ends in a crash report. A background job that can never return — a read from a share or a WSL path that has hung, a Docker call with no timeout — was waited for 8 seconds at close and then left running, and Qt ended the process on it (`QThread: Destroyed while thread is still running`, an abort: a core dump on Linux, a crash report on Windows and macOS). Now, after Yu'lon's usual close waits (any server tab's, log panel's and the update check's own, then 8 seconds for each job still running), Yu'lon writes which job was still running into `yulon.log` — a log panel by its job's title, the update check by name, any other job by the work it was doing — ends any `docker logs` child it had left open, flushes the log and leaves with exit code 0. The forced exit loses nothing the old crash kept: the window is already closed, and Yu'lon saves its state when you act, not when you close. An install still running when you close is cut off, exactly as it was before. A close where every job finished is unchanged. Proved on Linux (WSL Ubuntu, Python 3.13, and m910q, Python 3.11) by starting the real app window, giving it a job blocked on an event nobody sets and closing it: exit 134 with the Qt abort 8.3 s after the close before, exit 0 8.0 s after the close now, with the job named in the log file. **Not measured:** the packaged build on Windows or macOS, where the same exit path runs. (T113, `t113-clean-exit-*`)
- With a controller connected — every Steam Deck — the app could crash when it closed, or when the controller went away. The reader that polls the pad ran on a background thread that was torn down the way the app's other threads stopped being torn down after the GUI segfault: it was destroyed along with the window even while still running, the app waited only half a second for it at exit, and its worker was freed from its own thread. Now the thread is held until it has really finished, released on the app's main thread, and joined at exit like every other background job. Stopping and restarting the reader also waits for the old one to let go of the controller before the new one takes it. Proved with a stand-in controller on a desktop: of ten tests, the old code failed nine — seven by aborting (exit 134) or segfaulting the app, two on an assertion — and the new one passes all ten. On a Linux test box, the real app with the real SDL library and a virtual Xbox 360 pad (the way Steam Input presents a Deck's pad) started its reader and closed cleanly 20 times out of 20; the old code also closed cleanly there, so the crash needs the slower or stuck controller shutdown the tests stand in for. Not yet on a Deck (T111, `t111-gamepad-thread-*`)
- Walking the Characters list no longer freezes the window for half a second per row. Choosing a character read what it is wearing (for the "Send N worn items" button) with two `docker exec` database queries on the window's own thread -- about 240 ms each on Docker Desktop, measured on `yulon-win11` with a 900-character bot server -- so every arrow key, and every list refresh that kept a row selected, stalled the app. The read now runs in the background; the button says "Reading what X is wearing…" until the answer lands, and an answer about a row you have already left is dropped. Proved on `yulon-win11` with a bundle built the way the release is: over 30 row moves, py-spy put the window's thread inside those queries for 21 of 60 seconds before the change and for none after (the reads ran on a worker instead, and the 30 button labels were the same), and a 35-minute run of tab switches and refresh presses stayed responsive throughout (T96, `t96-windows-freeze-*`)
- Sending gold to a character no longer crashes the app. The Characters tab re-reads its list after every action that works (gold, teleport, level, revive, rename, gear), and that re-read cleared and refilled the list from a background thread while the window was drawing it, which is undefined behaviour in Qt. On a server with hundreds of bots the list is long enough for the two to collide: on a TBC box with 900 characters, pressing Send gold on the real tab crashed the app in 4 of 5 runs (once after a single press) and froze the window for about 20 seconds when it did not crash. The server was fine the whole time: every mail arrived and the world never restarted. The list is now filled on the window's own thread. The Tuning panel's Restart and Recreate had the same flaw when they finished. The fix is in the part every tab shares: the app's background-job runner now hands every job's answer back on the window's thread itself, whatever kind of callback is waiting for it, so a tab can no longer get this wrong. Reported on Discord for Tortoise on Windows; reproduced and re-run on m910q against TBC, where the same presses leave the app alive. (T97, `t97-gold-crash-*`)
- A Tortoise server updated onto the new bots module keeps its bots. `Sagiroth/TortoiseBots` now runs only the bot accounts listed in its own registry table (its issue #265), and nothing fills that table for accounts an older module made, so an install moved onto it by "Update the server to latest…" booted with its 500 bots ignored and the module began building a second pool of 500 beside them. When that update (or "Return to the tested pin") moves the module, the press now ends by enrolling the older accounts with the module's own `bot pool adopt preview` / `bot pool adopt confirm` — over SOAP, which this core runs at console level, else at the attach console — and restarts the world, which is when the module loads them; if neither channel can reach the command, the last line says exactly what to type at the console. Measured on `yulon-ubuntu` against a finished install with its registry emptied: the app's update press moved the module `c591bbb` -> `554dc9b`, enrolled the 50 old accounts over SOAP and restarted, and the old characters came back online; the console fallback and the "type this" message are proved by unit tests only. The enrolment is saved as soon as it is made, so if the job stops before its restart, the next start of the server loads those bots. A confirm that got no answer is never sent again, on any channel: the world is restarted anyway, because on this core it has usually run (T123, `t123-tortoisebots-adopt-*`)
