# Changelog

Every release of Yu'lon, newest first. The **Unreleased** section is titled by the lead when a release is cut; until then it collects what has landed on the working branch since the last tag. Entries say what a player or operator can now do, and how it was proved on a real machine. The raw gate captures behind them are kept in the maintainers' local notes rather than in this repository, because they name our own machines and accounts; an entry says what was run and what it showed.

## Unreleased
- When **Re-extract map data** fails on a Centurion server whose pathfinding data had stopped part-way, the message now also says that its finished tiles were kept and that **Make the pathfinding data** on the Server tab continues from them. On a Linux test machine 35 tiles were kept and the next run continued from them, while the message only said the pathfinding data came back "if it had finished". The sentence is said only when the next run really continues from those tiles. The extraction tools' progress bars no longer leave `#` characters in the install log or in a failed tool's last words: a bar on a line of its own is left out, and one stuck to the front of the next line is taken off it. Proved by unit tests that fail a real Re-extract with a crashed, a stopped and an unrelatable pathfinding run, and that feed a failing extraction the output its tool wrote on the test machine; LIVE-PROOF-PENDING (T263)
- On Linux and the Steam Deck, a module's or keg's game client files, such as ARAC's `Patch-A.MPQ` or the Season of Discovery keg's patches, now replace a file already in your client under another case instead of being copied beside it. A client holding `Data/patch-a.mpq` got a second `Data/Patch-A.MPQ`, which the game, running under Wine or Proton, sees as two archives of one name, and **Remove** then took back only the new copy. Now each file lands on the name already there (`Data/patch-a.mpq`, `data/enus/` instead of a new `data/enUS/`), a name is only made when nothing of that name is there in any case, and **Remove** takes back the file under the name it landed on. If that name already holds a file of yours with other contents, for example another mod's `patch-a.mpq`, Yu'lon first renames yours to `patch-a.mpq.yulon-module-old` beside it, and **Remove** puts it back under its own name, unchanged and still read-only if it was. Before, the module's file was copied over yours, and **Remove** then deleted it, so your file was lost; a read-only file of yours stopped the install with an error. If Yu'lon cannot put your file back, **Remove** leaves it under the `.yulon-module-old` name and says so; it never deletes it. Yu'lon writes down where your file went before it moves it, so an install that fails or is cut off part way puts your file back before it reports the failure, and if even that is impossible, **Remove** finds the record and puts it back later. A module whose client file has the same name as a file another module already put there is refused, naming both, until the first is removed. An update that no longer ships one of its files takes that file back and puts yours back. **Uninstall** of a whole server now does the same for every module: their files leave your client and yours come back, and any file of yours it cannot put back is named in its result. A file shared with your own client by a ready-to-play client is replaced as before, and your own client keeps its file. An addon is copied into an `interface/addons` folder already there in the same way. Nothing else in your client is renamed, and read-only files stay read-only. Proved by unit tests that install and remove the shipped ARAC module, the Season of Discovery keg and an addon through Yu'lon's own module installer into real client folders named in lower and mixed case, over a file of the player's in the same and in another case, read-only, put back on Remove, and with a put-back that fails; LIVE-PROOF-PENDING (T262)
- On Linux and the Steam Deck, a game client whose `Data` folder is named `data`, as `unzip -LL` and some copy tools leave it, is now taken as a client. Linux tells `data` from `Data`, so the install check, **Set client folder…**, **Make a ready-to-play client…**, Play and **Refresh** all said the folder had no Data folder and was not a game client. Now Yu'lon finds that folder whatever its case, and your client keeps the name it has: nothing in it is renamed, and read-only files stay read-only. The server address goes into the `realmlist.wtf` already in that folder (`data/enus/realmlist.wtf`), or into a new one there, instead of into a second, empty `Data` folder the game never reads. Centurion's temporary copy of the client names the folder `Data`, the only name its map extractors read; TBC, Vanilla and Tortoise read it through the links T260 lays. A folder with no `Data` folder in any case is still refused. Proved by unit tests on real folders with a lower-case `data`: the install check of every game that makes map data, the real extraction of TBC, Vanilla, Tortoise and Centurion, the folder picker, the ready-to-play client and its Play and Refresh checks, and the realmlist writes; LIVE-PROOF-PENDING (T261)
- **Re-extract map data** on a Centurion server whose map data was already made now works, and a re-extraction that fails no longer leaves you worse off. On a Linux test machine the press made the maps again and then stopped at the next tool with "Your output directory seems to be polluted, please use an empty directory!", naming no folder, after it had already thrown away the pathfinding data and Yu'lon's record of the map data; every later press stopped the same way. That tool will not write into the `data/Buildings` folder a finished extraction leaves, and Yu'lon knew that rule only for the TBC and Vanilla tool. Now the press moves the old map data aside inside the server's `data` folder, so the tools start into empty folders, and keeps it until the new map data is in; only then are the old map data and the pathfinding data made from it removed. If the extraction fails, is stopped, or Yu'lon stops reading it part way, the old map data is put back as it was, with its record and with its pathfinding data if that had finished, and the server runs on it as before; a pathfinding run that was still being made, or had stopped part-way, keeps its finished tiles and continues from them. After a crash, the next press puts the old map data back first, unless the crash came after the new map data was complete. An **Install** press that would make Centurion's map data again over a finished `data/Buildings` now stops before running anything and names that folder, as TBC and Vanilla already did. Proved by unit tests that run the real press over a finished Centurion layout, and make it fail at a tool, at the start check, by closing it part way and after a crash, comparing every file under `data/` before and after; LIVE-PROOF-PENDING (T241)
- On Linux and the Steam Deck, WoW TBC, Vanilla and Tortoise now make their map data from a client whose game files are named in another case (`Data/expansion.mpq` or `Data/enus/locale-enus.mpq` instead of `Data/expansion.MPQ` and `Data/enUS/locale-enUS.MPQ`), as clients copied from Windows or unpacked by some tools often are. Proved by unit tests that run the real extraction step over real TBC, Vanilla and Tortoise client folders with lower-case and mixed-case names, opening each archive the way the map tools do from inside the container, and that compare every name, byte, date and permission in the client before and after; LIVE-PROOF-PENDING (T260)

- A server build that loses its connection to Docker, or stops printing anything, now tells you so in plain words instead of leaving you with a raw error or an empty wait. On a Windows test machine a Centurion build finished compiling, printed nothing for 53 minutes, and then failed with "the build failed (exit 1). Its last words were:" followed by Docker's "rpc error: code = Unavailable desc = error reading from server: EOF"; a later build failed the same way at 99 % and passed once Docker had more memory. That ending now says the build lost its connection to Docker's builder, that the commonest reason is Docker running out of memory while compiling, how to check how much memory Docker has (`docker info`) and where it is set (on Windows, `memory=` in `%UserProfile%\.wslconfig`, since Docker Desktop's WSL 2 engine has no memory slider), and that running the install or rebuild again picks up from the last finished step, which Docker keeps. Docker words a lost builder more than one way: on a Linux test machine a restart of Docker under a build ended it with "failed to solve: Unavailable: error reading from server: EOF", which Yu'lon first missed and answered with a bare "the build failed (exit 1)"; that wording, and the same EOF with no code in front of it, now get the same explanation, while a build step's own failure and a registry's "429 Too Many Requests" or "not found" do not. Proved by tests that replay both machines' last lines and a build that stays silent for 35 minutes; the first wording was seen live on the Linux test machine (T202)
- Pressing **Install** again after an install whose build failed is no longer refused for disk space that the build's own cache already takes. On a Windows test machine a Centurion install failed after its compile had finished, and the next press was refused with "free space on Docker's disk: 30 GB free, and the install needs 40 GB", while 12.91 GB of that disk was the compile Docker had kept and the next build would reuse; the only way through was clearing that cache and compiling again. Yu'lon now notes how much build cache Docker holds as a build starts, in `.yulon-build-cache.json` in the server folder, and keeps that first figure through further failed attempts until a build finishes, so a second failed build does not lose the credit for the first one's compile; the build step says it is asking Docker, which can take up to two minutes. When a press will run the build again, the free-space check counts the build cache added since then toward what the build needs, and says so on the line in both its own figure and Docker's. Cache that was already there, which can be another server's, is never counted, and the check never asks for less than a server whose build is finished. On a drive that holds both the server folder and Docker's disk, the same press is also credited with what the server folder already holds, up to the share of the space the folder is asked for: on a Linux test machine a WotLK install's next press was refused with "46 GB free, and the install needs 46 GB" while its 2.2 GB checkout was already in the folder. When two figures would round to the same whole number, the line now shows them with a decimal, so a refusal never reads as equal numbers.
