# Changelog

Every release of Yu'lon, newest first. The **Unreleased** section is titled by the lead when a release is cut; until then it collects what has landed on the working branch since the last tag. Entries say what a player or operator can now do, and how it was proved on a real machine. The raw gate captures behind them are kept in the maintainers' local notes rather than in this repository, because they name our own machines and accounts; an entry says what was run and what it showed.

## Unreleased
- Closing Yu'lon while something is stuck no longer ends in a crash report. A background job that can never return — a read from a share or a WSL path that has hung, a Docker call with no timeout — was waited for 8 seconds at close and then left running, and Qt ended the process on it (`QThread: Destroyed while thread is still running`, an abort: a core dump on Linux, a crash report on Windows and macOS). Now, after Yu'lon's usual close waits (any server tab's, log panel's and the update check's own, then 8 seconds for each job still running), Yu'lon writes which job was still running into `yulon.log` — a log panel by its job's title, the update check by name, any other job by the work it was doing — ends any `docker logs` child it had left open, flushes the log and leaves with exit code 0. The forced exit loses nothing the old crash kept: the window is already closed, and Yu'lon saves its state when you act, not when you close. An install still running when you close is cut off, exactly as it was before. A close where every job finished is unchanged. Proved on Linux (WSL Ubuntu, Python 3.13, and m910q, Python 3.11) by starting the real app window, giving it a job blocked on an event nobody sets and closing it: exit 134 with the Qt abort 8.3 s after the close before, exit 0 8.0 s after the close now, with the job named in the log file. **Not measured:** the packaged build on Windows or macOS, where the same exit path runs. (T113, `t113-clean-exit-*`)
- Stopping Docker itself with a server running no longer throws away the characters the world was still saving, and a Rebuild no longer takes the database out from under a running world. The app's own Stop always stopped the database last, but Docker's own shutdown signals every container at once, and the database was gone in under 2 seconds while the world was still writing: on a WotLK install with 500 bots the worldserver hit `Lost connection to MySQL server` the moment it began logging its bots out, and on Tortoise, which keeps its character tables on MyISAM, a save cut half-way leaves a character missing rows. The database now holds its shutdown until the world and login servers have disconnected (at most 4 minutes, so it fits inside the app's own 5-minute stop; a database that cannot be asked who is connected is retried and logged, and stops after five failures in a row) and has the world's 5-minute grace, on all four games; and the Rebuild's container replacement now stops the world and login servers first, where it used to replace the database while the world was still using it (the world lost its saves the same way). Proved on yulon-ubuntu with `systemctl stop docker` on Linux: the same WotLK install went from the save queue lost to `Waiting for 2198 queries to finish` drained in 32 s with no connection error, the database shutting down 0.2 s after the world closed its last connection; the app's Stop takes no longer than before (database down 0.5 s after the world) and the world starts again clean. The Rebuild's replacement on the same running install: 19.6 s before, with the old world losing its database mid-save (`Lost connection`, `Waiting for 0 queries`); 48.2 s now, 35.5 s of it the world draining 2145 queued saves with no error, and the database replaced after it with nothing to wait for. Tortoise's side ran on its real rendered compose file with a stand-in world: 0 of 9 saves landed after the signal before, 1286 of 1286 after. **Not measured:** Windows and Docker Desktop (quitting it, or shutting the PC down), and a Linux PC shutdown, where systemd stops the services under its own timeouts (on the Ubuntu box `docker.service` has none but `containerd.service` has the 90-second default, shorter than the 4-minute hold), so whether a world with a long save queue gets to finish there is untested. New installs have it. An existing WotLK install picks it up at its next *Update the server to latest…*, which rewrites the compose file; an existing Tortoise, Vanilla or TBC install does not yet, because nothing rewrites those compose files after the install. (T98, `t98-db-stop-grace-*`)
- Yu'lon installs the update it offers you. `Update now` downloads the file built for the computer you are on, checks it against the `SHA256SUMS` the release publishes, unpacks it inside your Yu'lon folder, starts that new copy once to prove it opens, and only then puts it in place and restarts into it — with a progress bar and a Cancel button throughout, and Escape means cancel rather than "carry on without me watching". A release with no `SHA256SUMS`, or one that does not list the exact file for your machine, is never installed: the button opens the release page instead. **Your own files in that folder are never touched.** Yu'lon replaces the files it shipped — the program and its `_internal` folder — one at a time, and never renames or deletes the folder itself; so if you unpacked the Windows zip straight into Downloads, or keep notes or saves beside the program, they stay where they are, and if the new version would have to replace something Yu'lon did not put there it stops and says so. Anything that goes wrong puts every file back exactly as it was and says why in a sentence rather than a traceback — a download that stops short, a checksum that does not match, an archive that is not a Yu'lon package or unpacks to something absurd, a new build that will not open. **An update that stops half way is reported at the next start and nothing is touched**: Yu'lon says what is missing and prints the steps that put the version you had back — it will not move those files itself, because that would be the running program renaming the files it is running from, with nothing to undo a half-done attempt. Those steps are written in one place and the app, `pylauncher/README.md` and the test that carries them out all read that one place, so what you are told is what has been proved to work; a version that brought a file the old one never had adds a step naming it. **Yu'lon also does not close until the installer has said it is running**: on a Windows 11 test box the installer was started and never ran, and the app closed anyway, leaving a shut launcher and no word — now it stays open and says it could not start the installer. The installer it waits for is the one it just started and no other: each attempt carries a secret the installer has to quote back, only one installer can hold the install at a time, and one that has not reported in within half a minute is called off, stopped, and its claim on the folder released — so a slow installer cannot come back to life and replace your files after Yu'lon has told you that nothing was changed, and the press Yu'lon then asks you for is not refused by what the last one left behind. If an installer cannot be stopped at all, Yu'lon says so and asks you to close and reopen it rather than sending a second one in beside it. Pressing Update now twice does one update, and each attempt writes exactly one installer script and takes it away again. On macOS, and in a folder you do not have permission to write, it downloads and checks the file and then opens it for you to install yourself. While it works, Yu'lon uses three hidden folders beside the program (`.yulon-new`, `.yulon-download` and `.yulon-old`); all three are gone the next time the new version starts, and Yu'lon will not delete a folder of that name that it did not create. Yu'lon never renames its own files while it is running: it writes a small helper that waits for Yu'lon to close first, and that helper is given the names as arguments and checks every one of them before it moves anything, so a path with a space, a quote or an `&` in it is a path and not a command. Two copies open at once will not both update, and nothing you can set and no environment variable changes where an update comes from. Pressed on real machines, each with a packaged build, each recorded as a dated measurement of the build it was made from: 2026-09-21 on Windows 11 (zip, unpacked flat into a folder of the player's own files), Ubuntu (AppImage and tar.gz) and Arch (tar.gz); 2026-09-21 on Windows 11 again once the installer had to prove itself before the app would close — the installer reported in with its secret, the app closed, the swap ran, the new version was on the desktop about five seconds later and said "Updated to Yu'lon 0.8.75-Public"; and 2026-09-22 on Fedora 44 (tar.gz and AppImage), the first presses on that distribution. In every one of them the player's own files in the folder were byte for byte as they had been and no working folders were left behind. The Windows presses are also where the launch flags were settled by measurement: the first spelling started the installer and it never ran, and the process-detach flag is refused outright under a scheduled task, which the app retries without. Which build each press was made from, and the press of the final build this work is merged as, are recorded in the pull request rather than here (T90).
- A release says what is in it and can be proved. Every `v*` tag now publishes a `SHA256SUMS` file beside its artifacts, and its release body is what this changelog gained since the previous `-Public` tag, under the headings it is written with, instead of a list of commit subjects; a tag whose changelog gained nothing keeps GitHub's generated notes, and nothing here can refuse a release. The packaged app also reports the tag it was built from rather than a hand-edited string — v0.8.68 shipped calling itself 0.8.66 — so the version a user sees, and the version an update check compares, is the version that was cut; the build asks the bundle it just made what version it thinks it is and annotates the run when that is not the tag, which is how the first attempt at this was caught (it stamped every runner correctly and shipped the old number anyway, because the packaging spec's `collect_submodules` had been silently collecting nothing for as long as it had been there). `yulon --version` answers without opening a window. Whoever cuts a release does nothing new for any of this. (T90)

- A server can be updated to its upstream's newest code, deliberately and with a backup offered first. "Update the server to latest…" sits beside "Rebuild the server…" on all four games and asks once: the dialog says in plain words that this builds code nobody has tested with this app, quotes the same measured compile times the rebuild does, and offers *Back up first, then update*, *Update without a backup* and *Cancel*, with Cancel as the default and as what Escape does. A backup that fails stops the update outright, and one that succeeds asks again before anything is fetched. Every source is checked before the first fetch — it must be the repository Yu'lon cloned, with no changes and no commits of your own in it, and a refusal names the files — and if the patch Yu'lon carries no longer applies, or the build fails, every source is put back on the commit it was on so the folder and the running server agree. - The install preflight stops telling a Linux user to open Docker Desktop. Four rows named a thing that exists only on Docker Desktop — "open Docker Desktop and wait for the whale icon" when the daemon did not answer, "raise the memory limit in Docker Desktop's Resources settings" under the memory floor, and "add the client folder to Docker Desktop's Settings → Resources → File sharing" on both arms of the client-sharing row — on a machine where there is no Docker Desktop, no Resources pane and no file-sharing list. Each now names what the machine it is printed on can actually do: a Linux box is told to start the service and to check its `docker` group, that a container gets the machine's own memory, and to look at the folder's permissions and mounts; Windows and macOS keep today's wording. A WSL distro is a third case and was getting the wrong half of both: its memory and CPU count come from Windows' `.wslconfig` whoever runs the daemon inside it, not from Docker Desktop's Resources pane, which is greyed out on that backend. Preflight now establishes which of the two Linuxes it is standing on — a machine or a distro — rather than guessing. It does **not** claim to know whose daemon a distro is running: Docker Desktop's through WSL integration and a `docker.io` installed inside the distro are both ordinary installs, nothing available here separates them, and the row that matters most refuses precisely because the daemon did not answer. So a distro is offered both routes on those rows, Docker Desktop first, which is also the hedge T37 wrote for the Docker-disk row and which stays. Found by reading, from the Codex review of T37 (T40, unit-proven; a sweep over every row on a Linux machine refuses the Docker Desktop vocabulary outright).

- Yu'lon tells you about public releases only, and shows you what is in one before you take it. It asks GitHub at most once a day (revalidated by ETag, so the usual answer costs nothing against the rate limit) and offers only tags ending `-Public`; a line under the header says a release exists, and `See what's new` opens the release notes of every public release between the version you are running and the one on offer, with `Open download page`, `Later` and `Skip this version`. (`8.2a-…` to `8.2e-…`, `tortoise-soap-yulon-arch-2026-09-09/`)
- **Accounts** — create, set a password, grant and revoke GM rank, through the tree's own writer; each tree's password scheme and rank scale measured rather than inherited. (`8.3a-…` to `8.3d-…`)

- **My Party (WotLK)** — a panel that adds a bot of a chosen class to your party through the server-side Lua bridge, shows the party as the group table reports it, and dismisses; every refusal in the app's own words. It now also lists the characters the playerbots module would accept as bots for your character — your own alts, guild mates, linked accounts — greyed with the reason where the module would refuse, and links two accounts so friends' and family's characters can be added; the live proof of both waits on a client seat (T26). All three arms pressed live. ### Fixed
- A server tab whose folder is gone can be dropped: "Forget this install…" appears on the Server tab only when the folder is confirmed absent (a file, a broken permission or a flaky network path do not count), asks once, forgets only the app's own record — Docker objects the app can no longer prove its own are left alone and named — and closes the tab; the same forget puts the record back if the state file cannot be written. And a Docker command aimed at a folder that no longer exists now says so instead of "Docker could not be found on this machine" (Windows reported the missing working directory as error 267, which the app read as a missing CLI). Two stale WotLK tabs on the Windows test box could not be removed before this (T34, unit-proven; the live press on `yulon-win11` is recorded on the ticket).
- A Yes on a question dialog was read as No: with the PySide6 this app ships (6.11.2) the static `QMessageBox.question()` returns a plain number rather than the button enum, and six places compared the answer by identity. So pressing Yes on "Install into this new folder?" opened the folder picker anyway, and Yes on the Rebuild, Apply-updates and Adopt confirmations was logged as declined and started nothing — the "rebuild does nothing" and "it makes me choose a folder whatever I choose" reports of 2026-09-11, on macOS and Windows, on `v0.8.0-Public`. A macOS user met the old sentence after a second install beside a running first one and could not tell the "other install" was their own.
