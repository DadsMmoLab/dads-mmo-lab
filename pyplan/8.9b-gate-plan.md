## The claim this box rests on, and what is left of it

8.9a's box says uninstall is gated on two families rather than four "because
the mechanism is the compose project and the folder, which are the engine's and
not the emulator's". **For the objects that is true, and it was checked rather
than assumed:**

| The mechanism | WotLK (`/home/pk/wowserver`) | Vanilla (`/home/pk/vanilla-75b`) |
|---|---|---|
| ownership record | `.yulon-install.json`, `install_id` `243c46e3` | `.yulon-install.json`, `install_id` `06ced116`, `family: cmangos` |
| project identity | `name: yulon-wow-wotlk-243c46e3` in `docker-compose.yml` | `name: yulon-wow-vanilla-06ced116` |
| label on the objects | `com.docker.compose.project` | same — `docker volume inspect yulon-wow-vanilla-06ced116_db-data` returns `com.docker.compose.project=yulon-wow-vanilla-06ced116`, and `docker volume ls --filter label=…` returns that one name and nothing else |
| container names | `ac-database`/`ac-authserver`/`ac-worldserver`, from `catalog.json` | `vanilla-db`/`vanilla-realmd`/`vanilla-mangosd`, from `catalog.json`; the spec is built per entry (`entry.container_spec()`) |

**For three relationships it is false**, and every one of them is a property of
the engine rather than of the emulator — which is to say they are inside the
very mechanism the box calls shared. They are the defect list below, and
`pylauncher/tests/test_uninstall_second_family.py` pins each of them now.

## What 8.9a's code gets wrong on this tree

### 1. BLOCKER — a ticked purge makes the reinstall impossible, not merely slow

`Uninstaller.run(keep_characters=True)` keeps `<project>_db-data` and then
deletes the server folder. On the AzerothCore tree that is the whole story:
`wow-wotlk`'s password plan is `fixed` (`"value": "password"` in
`catalog.json`), so a reinstall regenerates a compose file carrying the same
password and the kept volume opens.

Every CMaNGOS entry GENERATES a password per install and keeps it in
`.db_password` **inside the folder the purge deletes** (measured on
`~/vanilla-75b`: `-rw------- 25 bytes`, and the same secret again in plaintext
in `.env`). `composegen.install_id()` is a digest of the absolute path, so the
reinstall comes back to the *same* volume name — and
`CmangosInstaller._db_password` refuses at stage 3 of 13:

> `…/.db_password` is gone, but this install's database volume
> `yulon-wow-vanilla-<id>_db-data` still exists and was created with the
> password that file held. … `docker volume rm <volume>` deletes it, and every
> character in it.

So on this tree 8.9a's ticked path produces a database that nothing can ever
open and an install that cannot be reinstalled into its own folder — the
opposite of the box's first clause. This is not a discovery the gate has to
make: the same loop was driven twice on m910q on 2026-09-05 and is written up
in `catalog/families/cmangos.py` (`_patch_sources`' remedy docstring).

**What 8.9b owes.** The ticked path must preserve the key with the volume. The
cheap shape is to keep `.db_password` (and the `DB_ROOT_PASSWORD` line of
`.env`) out of the deletion — either by leaving those two files, or by copying
the secret into Yu'lon's config dir keyed by the volume name and restoring it
on the next install into that folder. Whatever is chosen, the dialog's
"Keep my characters" sentence has to be true on this tree for the same reason
it is true on the other. Pinned by
`test_the_cmangos_folder_holds_the_only_key_to_the_volume_a_ticked_purge_keeps`
and `test_the_reinstall_a_ticked_purge_promises_is_refused_on_the_cmangos_tree`.

*(This also answers 8.9a's open question 3 — "the CMaNGOS db-password refusal
… 8.9b owes that sentence". It owes more than a sentence: the refusal is
correct, and it is the purge that has to stop causing it.)*

### 2. BLOCKER-adjacent — the shared database image

`wow-vanilla` and `wow-tbc` both pull `mariadb:11`; `wow-wotlk` pulls
`mysql:8.4` and nothing else in the catalog does. On m910q both CMaNGOS installs
exist (`yulon-wow-vanilla-06ced116_db-data`, `yulon-wow-tbc-37f13213_db-data`),
and — measured — `docker ps -a --filter ancestor=mariadb:11` is **empty**: the
TBC install has no containers at all right now, so the daemon would NOT refuse
a removal, and the neighbour's next start re-pulls 458 MB over that box's
known-flaky link.

`purge.py` already does the right thing (`built_image_refs()` one ref at a time,
never `--rmi all`), so this is not a defect in the code — it is a defect in what
8.9a's gate can prove. 8.9a's box cannot see it: `mysql:8.4` is nobody else's.
**8.9b's gate must therefore assert `mariadb:11` survives**, and that is the
step whose failure would be silent on the other tree. Pinned by
`test_the_database_image_is_no_familys_to_remove_and_this_ones_is_shared`.

### 3. The record names a second folder here, and only here

`install.requires_client_dir` is true for the three CMaNGOS entries and absent
for `wow-wotlk`, whose client data is downloaded into a volume. So the
`state.json` row 8.9a forgets names exactly one folder on yulon-ubuntu — the one
it deletes — while here the same row names the user's own WoW 1.12.1 client.
`purge.py` never reads `client_dir` and `_for_vanilla()` does `del client_dir`,
so nothing does the wrong thing today; what is missing is a test and a gate step
that keep it that way, because any future "delete what the record names" would
pass 8.9a's gate and destroy a client folder here. `LEFT_BEHIND` already
promises "your WoW client folder" — 8.9b is the box where that sentence is
first true of an install that has one. Pinned by
`test_only_the_cmangos_tree_makes_the_record_name_a_folder_outside_the_install`.

### 4. What the ticked path costs is not the same thing

WotLK keeps its client data in a SECOND named volume (`client-data`, 3.2 GB);
the CMaNGOS tree extracts the user's own client into `./data` **inside the
folder** (2.4 GB on `~/vanilla-75b`), beside `src/` (410 MB of git checkouts).
So: enumerate the volumes, never name them — `docker volume rm` exits non-zero
on a volume that does not exist, and the sets differ by family (`purge.py`
already lists by label and removes what Docker returned, which is right). And
the ticked path here throws away an extraction and an mmap build that the
reinstall must do again, which is the whole reason step 8 below is the
expensive one. Pinned by
`test_the_two_gated_families_declare_different_volume_sets`.

### 5. A missing `.env` breaks every compose command on this tree

Measured on a COPY of the two trees' compose files, nothing started:

| | `docker compose down --dry-run` with `.env` absent |
|---|---|
| Vanilla | **exit 1** — `error while interpolating services.vanilla-db.environment.MARIADB_ROOT_PASSWORD: required variable DB_ROOT_PASSWORD is missing a value: Yu'lon .env is missing` |
| WotLK | **exit 0** — the dry run lists all five containers |

The CMaNGOS template uses `${DB_ROOT_PASSWORD:?…}` (deliberately: it refuses to
start a database with an empty root password), and compose interpolates on
`down`, `ps` and `config` as much as on `up`. Consequences for the purge, both
survivable: `remove_staged()`'s `compose down` fails and falls back to stopping
and removing by name — which still uses the full 300 s grace, and still works,
because `_project_containers()` asks `docker ps -a` and not compose — and
`logsnap.capture()`, which resolves its container through `compose ps`, reports
a snapshot problem instead of a log. Worth a gate step because "the fallback
carried it" is a claim about a warning line nobody has ever read on this tree.

### 6. Networks are a fifth object nobody counts

`compose down` removes the project's networks; the definition of done names
"container, volume, image, folder or record". If the compose path fails (item 5)
the by-name fallback leaves the network behind, and the box would still be
ticked. m910q already carries `yulon-wow-tbc-1cbfa4ac_tbc-net` — an orphan
network for an install with no volume, no image and no folder. **8.9b's
"nothing remains" check includes `docker network ls`.**

### 7. A dry run on this box prints a lie about networks

Compose v5.5.0 on m910q printed, inside `--dry-run`, two lines with no
`DRY-RUN MODE -` prefix:
`Network yulon-wow-vanilla-06ced116_vanilla-net Removing` / `Removed`. **The
network was still there afterwards** (`docker network ls`). Every other line of
that run carried the prefix. Anyone reading a `--dry-run` transcript into gate
evidence on this box will record a removal that did not happen; ask
`docker network ls`, never the transcript.

## The steps

8.9a's ten, in the same order, with this tree's differences called out. Steps
1-5 are cheap and prove the refusals; 6-9 are the destructive sequence.

1. **Ownership — UNKNOWN.** As 8.9a step 1 (truncate the claim; then a
   `"version": 99` claim, whose refusal must carry `read_claim()`'s own
   reason). Same file, same shape on this tree.
2. **Ownership — UNCLAIMED.** Adopt a hand-made CMaNGOS-ish folder through
   "Use existing…" and press Uninstall. Refused, folder still there.
3. **The running refusal.** Start the throwaway, press Uninstall. The refusal
   must name `vanilla-mangosd`, `vanilla-realmd`, `vanilla-db` — the names come
   from `catalog.json`, so this is where a spec built from a constant instead of
   from the entry would show. Screenshot; all three still up afterwards.
4. **The copied install.** `cp -a ~/gate89b/server ~/gate89b/copy`, adopt the
   copy, press Uninstall: refused as UNKNOWN (the copied claim names the
   original's id). `rm -rf` the copy afterwards.
5. **The plan reads only.** Press Uninstall… and stop. It must name the folder,
   a size within 10 % of `du -sh`, the project, three containers, **one** volume
   and **one** image. Baseline unchanged afterwards.
   **5b — the failed install.** `~/vanilla-75`'s shape is the commonest thing a
   user uninstalls: OWNED claim, four stages completed, `last_error` naming the
   vmap extractor, an image, a folder — and **no containers and no volume**
   (measured 2026-09-08). Make a copy of that shape at `~/gate89b/failed`,
   adopt it, tick the box and press: today `run()` raises "cannot identify this
   install's database volume". Record the wording. If it reads like a fault
   rather than "there are no characters here to keep", that is the sentence to
   fix.
6. **Ticked — the characters survive.** Tick, press. Checked in order:
   1. a log snapshot with this install's id and this run's timestamp, non-empty;
   2. no containers of the project (`docker ps -a --filter label=…` empty);
   3. `<project>_db-data` **still there**, same size as baseline;
   4. the one built image gone;
   5. **`mariadb:11` still there** (defect 2), and `mariadb:10.6`, `alpine/git`
      with it;
   6. `~/gate89b/server` gone — **except whatever the fix for defect 1 keeps**;
      whatever that is, `sha256sum` it against the baseline;
   7. `state.json` no longer names it, the tab is gone, the tile reads Install;
   8. `docker network ls`: `<project>_vanilla-net` gone (defect 6).
7. **Nothing outside the three things.** Diff every listing against
   `00-baseline.txt`. Still present, explicitly: `~/vanilla-75b` and its project,
   volume and image; `~/tbc-7.4c`'s volume; the Tortoise project; `mariadb:11`;
   `~/.local/share/yulon/backups`; **the client folder this install was
   installed from, with its `Data/` intact** (defect 3 — 8.9a's box has no such
   folder to check).
8. **The reinstall finds the characters.** Reinstall Vanilla to
   `~/gate89b/server`. This is the expensive step on this tree and there is no
   shortcut: the folder held `src/`, `data/` and the state record, and the image
   was removed, so the press re-clones, recompiles, re-extracts, rebuilds mmaps
   and re-imports. Pass:
   1. the regenerated compose carries the SAME `name:` as G3;
   2. **stage `db-password` does not refuse** — the whole point of defect 1's
      fix, and the step that fails today;
   3. `docker volume ls` shows the pre-existing `_db-data` (compare creation
      timestamps, not names);
   4. the import stage finds the databases populated;
   5. **the character from G5 is on the login screen.** Screenshot.
   Record the wall time and the per-stage split; it is the number the owner
   needs for open question 1.
9. **Unticked — nothing remains.** New character first, then untick and press.
   Everything in step 6, plus the volume gone and the network gone. Diff against
   baseline again.
10. **Leave the box as it was found.** Nothing of 8.9b's own should be left
    running; `~/vanilla-75b` stopped, as the owner rule for m910q requires.

## What this gate proves that 8.9a's cannot

* a family whose database password is **generated per install and kept in the
  folder** (defect 1) — the only tree where "keep the volume, delete the folder"
  is a contradiction;
* a **shared** pulled database image with a live neighbour (defect 2);
* a record that names a **second folder outside the install** (defect 3);
* a project with **one** volume rather than two, which is what makes
  "enumerate, never name" testable in the failing direction (defect 4);
* a compose file whose interpolation makes `down`/`ps` fail without `.env`
  (defect 5).

## Open questions for the owner

1. **Where does the throwaway come from?** The box says 8.9b consumes "the
   shared fresh throwaway install at the end of that box's sequence", but
   8.9a's sequence ends with a **WotLK** install on yulon-ubuntu, and this box
   gates on m910q. 8.1c's line reads the other way — owner answer 12,
   2026-09-06: "keep a fresh throwaway install for 8.9b alone". No such Vanilla
   install exists on m910q today (`~/vanilla-75b` is the gated one,
   `~/vanilla-75` is a failed one), so **G1 is an install press the owner has to
   start**, and it is the long pole of this box.
2. **Does the ticked path keep the extraction too?** Keeping `db-data` on WotLK
   costs the user a `client-data` re-download; here it costs a recompile, a
   re-extraction and an mmap build. If the answer is that "Keep my characters"
   should keep `./data` and `src/` as well, the action stops being "delete the
   folder" on this tree and the dialog has to say so.
3. **8.9a's open questions 1, 2 and 4** (which volume the checkbox is on, the
   per-install sidecars, cancel semantics) are unchanged here and are not
   re-asked.
