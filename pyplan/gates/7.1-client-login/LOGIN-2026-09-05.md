The second time clause 14 was met, on a different server than the first: the install
that 7.2's clean-box gate rebuilt on `yulon-ubuntu` from the `clean-ssh` checkpoint in
the small hours of 2026-09-05. Same laptop client, new account, new route.

* **Client**: `C:\wow335ahd`, 3.3.5a build 12340, on the laptop.

## The route, and why it was not Tailscale this time

The `clean-ssh` checkpoint predates Tailscale on that box, so the restore took it away:
`tailscale ip -4` on the box answers `command not found` (`server-side-20260905.txt`).
The 09-04 login went to `100.71.125.58`, an address the box no longer has.

So the login went through an ssh tunnel instead: `ssh -L 3724:127.0.0.1:3724
-L 8085:127.0.0.1:8085 yulon-ubuntu`, with the realm row set to `127.0.0.1` for the
duration (the address a client is *sent to* after auth has to be one it can reach, and
through a tunnel that is loopback) and `Data/enUS/realmlist.wtf` on the laptop set to
`127.0.0.1`. The client's own log shows exactly that:

```
9/5 07:31:41.125  GRUNT: state: RESPONSE_CONNECTED result: LOGIN_OK 127.0.0.1:3724
9/5 07:31:41.385  GRUNT: state: LOGIN_STATE_AUTHENTICATED result: LOGIN_OK
9/5 07:31:41.902  ClientConnection Completed: COP_AUTHENTICATE code=AUTH_OK result=TRUE
9/5 07:31:42.568  ClientConnection Completed: COP_GET_CHARACTERS code=44 result=TRUE
```

(`client-connection-20260905-0731.log`, the whole file; the 09-04 log had been moved
aside as `connection.log.before-0905` first and is byte-identical to
`client-connection-20260904-2030.log`.)

This is the owner's "make it possible to set it to 127.0.0.1" case, exercised for real:
a loopback realm is a legitimate configuration, not only a mistake (bug-checklist §41).

## The server's own record

```
| id  | username  | last_login          | last_ip    | online | failed_logins | joindate            |
| 102 | GATELOGIN | 2026-09-05 05:31:40 | 172.18.0.1 |      0 |             0 | 2026-09-05 05:28:33 |
```

`05:31:40` UTC is the client's `07:31:41` CEST — the same event, one second of clock
skew. `failed_logins=0`: first try. `last_ip 172.18.0.1` is docker's bridge gateway:
the tunnel delivers to the VM's loopback and the container sees the bridge, so the
client's address is not recoverable from this row on either route. `online` is `0`
because this was captured at 10:17 CEST, long after the client was closed
(`server-side-20260905.txt`, read-only, `docker exec` + `SELECT`).

AzerothCore's `Auth.log` and `Server.log` at their default level do not name the
account, so there is no third witness; the two above agree with each other.
