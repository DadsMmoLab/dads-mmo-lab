## 2. Recommendation on 7.1's Ubuntu sub-gate: **do not tick**

The evidence set records a genuinely good result — a from-scratch AzerothCore + playerbots install on Ubuntu 24.04 that reached `ready` and exited 0 in 45 minutes, with a correctly-behaved consent prompt and a correct re-login refusal. That is worth committing and worth keeping. It is **not the gate line**, and ticking it would mean asserting six things no reader can re-derive and two things the logs actively refute.

**What is missing, precisely:**

- **A starting-state capture.** One line inside the `script(1)` session before press 1: `docker --version; systemctl is-active docker; id -Gn; ls -d ~/wowserver`. Without it, "clean checkpoint" is unfalsifiable — and 7.2's "same checkpoint" is unfalsifiable twice over.
- **Provisioning stdout.** The window `gate-press1.log:16` (14:29:29) → `:17` (14:30:19) is 50 seconds of total silence because `_run_steps` at `12b7ebb0` collects apt output instead of streaming it. Every package-version claim in the report lives in that silence. (Shape note: ~30 s of that window is `_wait_docker_ready`'s full budget, which *cannot* succeed in press 1 because the process's own supplementary groups do not change when `usermod` runs — the code says so at `platform.py:1348-1354`. That leaves ~20 s for the whole apt transaction. Plausible on a warm mirror, but nobody can check.)
- **The auth container's log.** `docker compose logs ac-authserver` redirected to a file. This is the single artifact the `127.0.0.1:8085` and `no UPDATE` clauses both turn on, and neither exists.
- **The account and client-login steps.** Never performed.
- **The LAN step.** Never performed — the realm stayed on loopback.
- **A real compose diff.** Against a fixture minted from a *different* run. Compare `pyplan/checklist.md:333`, which records the Arch equivalent honestly ("Compose diff **PASS (57 passed)**"); nothing of that form exists for Ubuntu, and `checklist.md:372-374` already lists this as owed.
- **A rewritten "resume" clause.** See below.

**The clause that needs re-scoping, not re-running.** "sudo dialog once" **cannot be satisfied on yulon-ubuntu at all** while `pk` has `NOPASSWD: ALL`. Two honest options, and the maintainer should pick one rather than let the clause sit un-ticked forever:

1. **Move it to a password-sudo box.** `SudoSession`'s own docstring (`platform.py:2429-2432`) names clean Fedora and Arch as the platforms the path exists for; per the project's one-distro-at-a-time rule, park the clause on the Fedora gate.
2. **Keep it on Ubuntu but stage the box** as the E.3 brief actually specified (`task-E.3-brief.md:78`): move `/etc/sudoers.d/pk` aside, add `pk` to `sudo`, re-run press 1. This is owner-approved in the brief and takes minutes.

What must **not** happen is what the report currently does at `gate-e3-report.md:334`, which lists "No sudo password dialog on a passwordless box" under **PASSED** for a criterion that asks for the dialog to *appear*.

**And the "resume skips the compile" clause is mis-worded, independent of any re-run.** The line compresses four presses into one clause and gets the mapping wrong twice: `ready` was press 3 and press 4, not press 2; and the press that skips the compile is press 4 (a re-press of a *complete* install), not the resume. Press 3 — the actual resume-after-kill — re-entered the build step, re-ran cmake from scratch in a fresh BuildKit stage (`gate-press3.log:160-168`), and re-issued every one of the 1829 ninja edges. What it *did* achieve is real and worth stating as its own criterion: **after a mid-compile SIGKILL, the resume recovers roughly 1315 edges from the BuildKit ccache mount in ~13.9 s** (`gate-press3.log:159` shows `--mount=type=cache,target=/ccache,sharing=locked` with `CMAKE_CXX_COMPILER_LAUNCHER="ccache"`; `:1624` is edge 1314 at `#25 13.87`, `:1626` is edge 1316 at `#25 28.41` where real compilation resumes) **and finishes in 610.7 s instead of the hours a cold build takes.** Reword the clause to that, and press 3 carries it on the lines above. Note the mechanism is evictable Docker build cache, not install state — a `docker builder prune` between the kill and the resume would have cost a full compile. If the checklist wants this re-derivable, a `ccache -s` capture is the missing artifact; there are no hit/miss statistics anywhere in the set.

## 3. Recommendation on 7.2's gate: **do not tick**

7.2 reads "full checks green; 7.1's Ubuntu gate re-run from the same checkpoint with no other change."

**How I read the line, and why.** "Re-run from the same checkpoint with no other change" is a *reproducibility* clause: it asks for a second, independent execution of 7.1's Ubuntu procedure from an identically-restored VM state, at the 7.2 code, so that any difference in outcome is attributable to the 7.2 changes and nothing else. Read that way, **one run cannot satisfy both lines**, and this directory contains one run.

The only reading under which this evidence could satisfy 7.2 is that presses 2/3/4 count as "re-runs" of press 1. That reading must be rejected on the evidence: they are not runs from the same checkpoint, they are *continuations* of one accumulating install state — `gate-press3.log:14` `Using /home/pk/wowserver (resuming)`, `gate-press4.log:15` `Already finished: clone-core, clone-modules, generate-compose, build, client-data, import`, and free disk falling 75 GB → 67 GB → 53 GB across them (`gate-press2.log:8`, `gate-press3.log:8`, `gate-press4.log:8`). Each press starts from a materially different machine than the last. That is the opposite of "the same checkpoint."

Independently of the re-run question, **7.2 inherits every gap in section 1**. A re-run cannot be shown to start "from the same checkpoint" when the first run never recorded what its own starting state was; and "full checks green" has no committed artifact either — the report's "1320 passed, 2 skipped, 16 deselected in 35.01s" (`gate-e3-report.md:22`) is nowhere in the evidence.

One useful consequence: a proper 7.2 re-run would *naturally* produce the second, independent compose capture that clause 10 needs to stop being circular. Sequence the work so the 7.2 re-run supplies it.

## 4. What the report claims that the logs do not support

This is the section to act on. Blunt, grouped, each with what the log actually says.

**Contradicted by the logs — these are wrong, not merely unsupported:**

1. **`gate-e3-report.md:131` "The resume did not re-compile. RESULT: PASS."** and its restatement at `:338-339`. The resume re-compiled. `gate-press3.log:36` is the build banner, `:292` is `[1/1829]`, `:2174` is `#25 DONE 610.7s`, and 1750 `Building CXX` lines run through `[1829/1829]`. Press 3's build took 610.7 s against press 2's killed build's 614 s — the same wall clock.
2. **`gate-e3-report.md:131` "continued from 1314 — where it was killed."** Numerical coincidence, not a hand-off. Press 2's edge 1314 is `TravelAction.cpp.o`; press 3's edge 1314 is `Linking CXX executable src/tools/mmaps_generator` (`gate-press3.log:1624`) and `TravelAction.cpp.o` is edge **1309** (`:1619`). Ninja indices are scheduling order and are not stable across runs.
3. **`gate-e3-report.md:338-339` "1294 objects replayed in 13.6 s."** *Trap #1, fired.* 1294 is a ninja **edge index** quoted as an **object count**. Of the first 1295 edges, 14 are `Linking` steps and one is a shell edge; the honest object figure is ~1280. A running counter has been reported as a count of one kind of thing.
4. **`gate-e3-report.md:131` "1294 objects replayed from the persisted build tree."** Nothing persisted a build tree. `gate-press3.log:160-168` is a cold cmake configure (compiler identification, ABI detection) in a new container. 5. **`gate-e3-report.md:99` "16 parallel compilers on 19.5 GB completed with no OOM,"** written in the **press-2** section about a run that was SIGKILLed at 1314/1829. True of press 3. It sits above a directory whose largest artifact, `gate-press2.log` (372 KB), ends in exit 137 — the report's headline is exactly the "filename says install, contents record a kill" shape the project watches for.
