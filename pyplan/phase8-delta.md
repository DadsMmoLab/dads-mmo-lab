## Facts that govern every row

1. **Yu'lon's only command channel today is one `docker attach` per command.** `controller_wow_wotlk/console.py:send_command` spawns an attach client, waits `_ATTACH_SETTLE_SECONDS` 0.6 s (`:45`) then a fixed `_DEFAULT_WINDOW_SECONDS` 3.0 s window (`:76`, `:322`), kills the client (`:328`) and cuts the reply out by the console's own prompt (`_parse_reply`, `:468-527`). The header at `:10-12` says nothing reads the stream while it arrives. It sends only where a pty exists (`can_send`, `:156-164`); Windows without a WSL-resident server cannot send, and the Console tab disables Send there (`ui/controller_view.py:1292-1300`). The three CMaNGOS controller packages delegate to the same transport (`controller_wow_tbc/console.py:63-87`, `controller_wow_vanilla/console.py:76-106`, `controller_wow_tortoise/console.py:56-82`). Every feature below that needs many small commands with typed replies is built on a channel that costs ≥ 3.6 s per command, allows one writer, and cannot separate a reply from bot-login noise (`console.py:485-486`, `:522-527`).
2. **Nothing in the tree enables SOAP.** The whole `pylauncher/` grep for `SOAP`/`7878`/`Ra.Enable`/`Console.Enable` yields `catalog/catalog.py:670` (`soap_port` default 7878, set by no entry), `catalog/composegen.py:369` (the token), and `catalog/installers/wow-wotlk/native/base.yml.tmpl:264` (the host mapping `${DOCKER_SOAP_EXTERNAL_PORT:-127.0.0.1:{{SOAP_PORT}}}:7878`), whose comment at `:259-260` promises "a later SOAP setup" that does not exist. The WotLK compose therefore publishes a container port nothing listens on. The three CMaNGOS entries patch no `SOAP.*`/`Ra.*` key (`catalog.json`, the `conf` tables) and publish no such port.
3. **What turning SOAP on costs, per tree.** AC: `SOAP.Enabled = 0` in `worldserver.conf.dist:453`, and every `AC_<KEY>` env var maps generically to a conf key (`src/common/Configuration/Config.cpp:435-438`, `:510-527`, `:540-552`) — so `AC_SOAP_ENABLED=1` in the override env is one line, the same mechanism the catalog already uses for `AC_AI_PLAYERBOT_MAX_RANDOM_BOTS` (`catalog.json:58-60`); the handler needs an account with `account_access.gmlevel ≥ 3` (`ACSoap.cpp:103-107`), runs the command with **no** level check because a console handler has no session (`Chat.cpp:52-56`, `ChatCommand.cpp:513-517`), queues it on the world thread and blocks (`ACSoap.cpp:120-130`), returns the print buffer or a sender fault carrying the same text (`:133-140`). TBC and Vanilla: SOAP compiled in unconditionally (`src/mangosd/CMakeLists.txt:24`), `SOAP.Enabled = 0` / `SOAP.IP = 127.0.0.1` / `SOAP.Port = 7878` in the dist (TBC `mangosd.conf.dist.in:1858-1860`, VAN `:1724-1726`), enabled by one conf key Yu'lon's `families/conf.py` table can patch; auth = basic user/password then `account.gmlevel ≥ SEC_ADMINISTRATOR` (`MaNGOSsoap.cpp:78-97`, `MaNGOSsoap.h:49`); the command runs at `SEC_CONSOLE` regardless of the caller (`MaNGOSsoap.cpp:113`), on the world thread, blocks (`:127-128`), returns output or a fault with the same text (`:135`, `:140`); one request at a time (`:51-63`). **Tortoise: no SOAP and no RA at all** — `src/mangosd/CMakeLists.txt:19-30` is the complete source list and `dep/src/CMakeLists.txt:19-25` the complete dependency list, neither names gsoap or `RASocket`. Its only remote channel is a **`pending_commands` table in `tw_logon`** polled every 60 s (`src/game/World.cpp:2724`, `:845`), 250-character commands (`sql/create_databases.sql:2572-2578`), run at `SEC_CONSOLE` with account id 0, **no output returned to the caller** (`World.cpp:3946-3948`), keyed by `RealmID` from `mangosd.conf` (`Master.cpp:799`; dist default `RealmID = 1`, `mangosd.conf.dist.in:8`).
4. **Every command channel executes on the single world thread and is serialised.** AC console, RA and SOAP all `QueueCliCommand` (`CliRunnable.cpp:231`, `RASession.cpp:200-204`, `ACSoap.cpp:121`) into one `_cliCmdQueue` (`World.h:221`) drained once per `World::Update` (`World.cpp:1341`, `:1641-1657`). TBC/VAN: `World.cpp:1748`, `:2229-2240`. TW: `World.cpp:3079`, `:3913-3922`. Only direct MySQL reads bypass it. The one thing that does not queue is mod-playerbots' **Playerbot Command Server**: an unauthenticated line-oriented TCP listener on its own detached thread (`PB src/Bot/Cmd/PlayerbotCommandServer.cpp:62`, `:67`, `:96-97`), bound to `0.0.0.0:8888` **by default at the pinned rev** (`conf/playerbots.conf.dist:2517`, `PlayerbotAIConfig.cpp:468`); it accepts only `<command>,<bot guid>` for a bot that is already loaded (`RandomPlayerbotMgr.cpp:2981-2999`). Yu'lon's compose publishes only 8085 and 7878 for the worldserver (`base.yml.tmpl:256-264`), so 8888 is not host-reachable, but it is open inside the compose network. The CMaNGOS module defaults it to 0 = disabled (`PBC PlayerbotAIConfig.cpp:277`; `aiplayerbot.conf.dist.in:972-973`).
5. **The attach console cannot see playerbots output on the CMaNGOS lineage.** The `.rndbot` handler sends its output back only when the caller has a non-zero account id (SOAP, RA, in-game); the stdin console (account id 0) gets it in the log alone (`PBC RandomPlayerbotMgr.cpp:3396-3401`, `:3446-3451`; same in the Tortoise copy, `TW modules/mod-playerbots/src/playerbot/RandomPlayerbotMgr.cpp:3620-3625`). Tortoise, having no SOAP, therefore has **no channel that returns bot-command output**.
6. **On AzerothCore, `.playerbots rndbot` never answers anyone.** Its handler discards the `ChatHandler` and logs with `LOG_INFO`/`LOG_ERROR` (`PB RandomPlayerbotMgr.cpp:2377`); its usage string advertises `add`/`remove` that the handler map does not contain (`:2387` vs `:2420-2431`).
7. **The Rust launcher's My Party and four of its GM tools are mod-ale Lua bridge commands, not `.playerbots` commands.** `dml_addclass`, `dml_uninvite`, `dml_whisper`, `dml_login`, `dml_gm_money`, `dml_gm_health`, `dml_gm_revive`, `dml_summon_npc` (`RUST party.rs:175-250`, `soap_cmds.rs:190-211`), deployed as `cli/lua/{party,gm}/*.lua` into `env/dist/etc/modules/lua_scripts/` by `bridge_setup_stream` (`RUST bridge.rs:141-226`). A `git grep` for a `.playerbots` worldserver command across `crates/` and `launcher/src-tauri/` finds none. The bridge's own notes record it being exercised live on Ubuntu on 2026-08-20 and **failing**: the comment at `bridge.rs:189-195` is the silent-bridge bug, in which the deploy reports success while every bridge command answers "Command does not exist", because the shipped `ALE.ScriptPath` is relative and the worldserver resolves it against a directory where nothing is. Two more ways it silently did nothing are at `:60-65` and `:365-367`. **Nothing in this repository records the bridge ever answering successfully, on any box.** Yu'lon's `mod-ale` manifest names the repo with **no branch and no rev** (`manifests/wow-wotlk/modules/mod-ale.json:9-11`), and patches a conf key `ALE.EnableLuaEngine` that the module's `mod_ale.conf.dist` does not have (`mod-ale.json:23-25` vs `ALE conf/mod_ale.conf.dist:63-71`); the compiled default of `ALE.Enabled` is `false` while the dist comment says `true` (`ALE src/LuaEngine/ALEConfig.cpp:20`).
8. **Command security levels are a database question on every tree but Tortoise.** AC overrides `RequiredLevel` from `acore_world.command` at load with a warning (`ChatCommand.cpp:118-124`) and per-account RBAC rows; TBC/VAN read `SELECT name,security,help FROM command` (`TBC Chat.cpp:1071`, `VAN Chat.cpp:1028`); the DB repos were not read. The `SEC_*` levels below are the shipped source/seed defaults.
9. **Yu'lon writes to the auth database while the server runs, through three paths and with no stop guard**: `accounts.create_account` (auth only; `accounts.py:111`, `:420-509`), the Networking tab's realmlist `UPDATE` (`networking.py:3617-3632`), and module SQL through `apply.Applier` into any of auth/characters/world/playerbots (`apply.py:1359-1387`; no `status` check anywhere in the file). Restore is the only write that refuses while world/auth are up (`maintenance.py:921-931`). Every read goes through `apply.DockerSql.query` (`apply.py:504-528`) or `maintenance.DockerMysql` (`maintenance.py:252`), both `docker exec … mysql` over stdin.
