## The one rule this gate is built around

**Never the finished 7.2 install.** Every step below runs against a THROWAWAY
install at a folder created for this gate, and the first thing the run sheet
does is prove which folder it is looking at. `/home/pk/wowserver` — the real
install, 2.3 GB, five containers, 6 GB of volumes — is not the subject of any
step here, and a step that finds itself pointed at it stops.

The throwaway install is **shared with 8.9b** and is consumed at the end of that
sequence. So 8.9a leaves it standing: step 9 reinstalls it, and 8.9b starts from
that reinstalled tree. The only thing 8.9a destroys for good is the copy it makes
in step 4.

## The steps

Each names the clause it proves, and the ground it starts from.

### 1. The ownership refusal — UNKNOWN

*Clause: "REFUSING when ownership cannot be proved through the tree's existing
three-valued ownership answer" (checklist 2506); "It does not act when ownership
cannot be proved" (decisions doc :195).*

Ground: G1–G4, server stopped.

Corrupt the claim: `truncate -s 12 ~/gate89a/server/.yulon-install.json`
(keep a copy first). Press **Uninstall…** on the tab.

Pass: the plan shows a refusal saying there is a record here Yu'lon cannot read,
the **Uninstall this server** button never appears, and `docker ps -a` /
`docker volume ls` are byte-identical to the baseline. Restore the claim file.

**Also run the variant the generic message would ruin**: put a claim file with
`"version": 99` in place. The refusal must carry `read_claim()`'s own `reason`
(a record written by a newer build) rather than the generic advice to delete the
file. Screenshot both refusals; they must not read the same.

### 2. The ownership refusal — UNCLAIMED

*Clause: same, and it is the half that is easy to get wrong. `UNCLAIMED` is not
permission — `state.json` records whatever folder "Use existing…" was pointed at.*

Ground: a SECOND folder `~/gate89a/adopted` holding a hand-made AzerothCore-ish
tree with no `.yulon-install.json`, adopted through **Use existing…**.

Press Uninstall. Pass: refused, with wording that differs from step 1's, and the
folder still on disk afterwards (`ls`). This is the step that would delete a
user's own server if the refusal had been written `if claim is UNKNOWN`.

### 3. The running refusal

*Clause: "a purge of a RUNNING server refuses and says to stop it first."*

Ground: G1–G4 with the server STARTED and the three containers up.

Press Uninstall. Pass: the plan refuses naming the running containers and saying
to stop the server first; `docker ps` shows all three still up afterwards, and
the `db-data` volume still exists. This is the refusal `phase8-decisions.md`
never mentions — it comes only from the checklist box — so it is worth a
screenshot in the evidence directory.

### 4. The copied install

*Clause: "It does not touch another install of the same game in another folder"
(:194); the danger `stop_staged()` measured end to end for Stop, whose
consequence here is data loss rather than a stopped server.*

Ground: `cp -a ~/gate89a/server ~/gate89a/copy` with the server stopped.

Adopt the COPY and press Uninstall in it. Pass: refused as UNKNOWN — the copied
claim names the original's `install_id` and the copy's path hashes differently —
and the ORIGINAL's project, containers and volumes are untouched. This is the
one step whose failure is unrecoverable in the other direction: a purge that
trusted the copied `name:` would delete the original's characters.

`rm -rf ~/gate89a/copy` afterwards; it is the only thing 8.9a destroys for good.

### 5. The plan reads only

*Clause: "`plan()` … READS ONLY" (:118-121).*

Ground: G1–G4, server stopped, baseline retaken.

Press Uninstall… and stop there. Pass: the plan names the folder, a size within
10% of `du -sh`, the project, the containers, both volumes and four images; and

### 6. Ticked — the characters survive

*Clause: "with the box ticked, a reinstall to the same folder finds the

Ground: G1–G5, server stopped, character recorded.

2. no containers of the project remain (`docker ps -a --filter label=…` empty);

### 7. Nothing outside the three things

*Clause: "It reaches nothing else on the machine" (:23); owner answer 1's

the real install's project and everything in it; `~/.local/share/yulon/backups`

### 8. The reinstall finds the characters

*Clause: the definition of done, and the whole chain the checkbox rests on.*

Ground: after steps 6 and 7, with `<project>_db-data` still on the daemon.

Reinstall WotLK **to the same folder** `~/gate89a/server`. Pass:
1. the regenerated `docker-compose.yml` carries the SAME `name:` as G3 — the
   install id is path-derived, so it must;
2. `docker volume ls` shows the pre-existing `_db-data` rather than a new one
   (compare creation timestamps, not just names);
3. MySQL skips its first-run bootstrap (the import stage should find the
   databases populated);
4. **the character from G5 is on the login screen.** Screenshot it. This is the

*Clause: "with it unticked, no container, volume, image, folder or record of the

Reinstall once more to `~/gate89a/server` and leave it standing, stopped. 8.9b

## What this gate cannot prove, and what to do about it

**The Windows read-only bit.** `remove_tree()` retries after clearing the write
bit and RAISES with a message naming the path when it still cannot finish — the
failure the Rust prior art swallows (`remove_title_fs()` is
`let _ = remove_dir_all(...)` on every branch, and Rust's `remove_dir_all` does
not clear `FILE_ATTRIBUTE_READONLY`, so it reports a successful uninstall having
deleted nothing). On Linux the retry is exercised through the POSIX shape of the
same stop — a directory with its write bit cleared — and the *failure* path is
skipped, because `chmod` on a directory does nothing on Windows and nothing on
Linux as root. **The Windows half is its own press on the gate box**, and its
run sheet is: install to `C:\gate89a\server`, confirm `.git` holds read-only
packs (`attrib` on a few objects), uninstall, and check that either the folder
is gone or the app says which path it could not delete. A silent success with
files still on disk is the failure.

**WSL-resident installs.** `purge` refuses them outright with a message naming
the distro: the folder lives inside the distro and `shutil.rmtree` cannot reach
it, and a purge that took the Docker objects and left the folder would leave an
install whose next purge has nothing left to prove ownership from. There is no
`wsl.exe`-side delete in this tree at all (`wsl.py` is all reads). Refusing is
the honest state; wiring the delete is a later box.

## The blocker found before the gate ran (2026-09-08)

`run(keep_characters=True)` kept `<project>_db-data` and then deleted the
folder — and on every `generated` entry the password that volume was created
with lives in `.db_password` INSIDE that folder. So the ticked path kept a
database nothing could open: `install_id()` is a digest of the absolute path, so
the reinstall lands back on the same volume, `resolve_secrets()` minted a fresh
password, and `CmangosInstaller._db_password` refused to write it beside a
volume that exists. The clause "with the box ticked, a reinstall to the same
folder finds the characters on the login screen" could not have passed on that
family. Found by the 8.9b lane reading 8.9a's own code, before the gate found it
the expensive way.

Fixed test-first, in three places:

* `yulon/dbsecret.py` (new) keeps one password per install under
  `config_dir()/db-secrets/<game>-<install id>.json`, owner-only at creation,
  recording the VOLUME it opens. The key is the same path-derived pair
  `channel_setup.credential_path()` uses, which is what makes it findable by a
  reinstall to the same folder and by nothing else.
* `purge.Uninstaller.run()` copies the password there **before the first
  destructive step**, and REFUSES a ticked purge whose password it cannot read
  — keeping a volume whose only key is already lost is the lie the copy exists
  to prevent. A `fixed` entry (`wow-wotlk`) copies nothing: its password is in
  `catalog.json`, which is exactly why this bug is invisible on the gated
  family.
* the reinstall reads it back: `StagedInstaller.resolve_secrets()` falls back to
  the copy when the file is gone, and `CmangosInstaller._db_password` writes the
  file back instead of refusing — but only when the copy names THIS volume and
  carries the value the spine resolved.

**What this adds to the live gate.** The ticked run must now leave
`db-secrets/<game>-<id>.json` behind, and the "reinstall finds the characters"
clause is the proof it is read back. WotLK is `fixed`, so the gate on this box
exercises the refusal-free path only; the copy-and-recall half is owed a press
on a CMaNGOS install, which is 8.9b's box.

Open question 2 below is unchanged in its answer and wider in its subject: the
kept password is a third per-install sidecar under the config directory, and it
is the only one this action WRITES. The dialog's "left behind" list names it.

## Open questions for the owner, raised by building this

1. **Which volume should the checkbox be on?** Yu'lon's "Keep my characters"
   keeps `db-data` (2.8 GB of characters). The Rust launcher's `--keep_data`
   keeps `client-data` (3.2 GB of downloaded maps) and NEVER removes the
   database — so its uninstall always keeps characters, as an orphaned volume
   no surface can find, and the user is never asked. The two designs ask a
   different question of a different volume. Step 8's re-download timing is the
   number that decides whether an unticked purge should also keep `client-data`.
2. **The per-install sidecars.** `credentials/<game>-<id>.json` and
   `logs/<game>-<id>-*.log` are keyed by the same path-derived id, so a
   reinstall to the same folder inherits both. After a TICKED purge that is
   right — same database, same account. After an UNTICKED one the credential is
   a secret for a database that no longer exists. Owner answer 1 says "only the
   launcher's own state record", so 8.9a leaves both and says so in the dialog
   rather than widening the answer on its own.
3. **The CMaNGOS db-password refusal.** It currently tells a user to run
   `docker volume rm …` in a terminal, and its own test says that should be
   re-pointed at the app "the day any part of the app grows such an action".
   That day is now — but uninstall is wired for AzerothCore only, so re-pointing
   it before 8.9b would send a CMaNGOS user to a button their tab does not have.
   **8.9b owes that sentence.**
4. **Cancel semantics** (`phase8-decisions.md` open item 4) are still undecided
   and 8.9a does not offer a cancel: the job runs to completion or raises. A
   half-cancelled deletion is worse than a finished one, and that is worth
   stating as the decision rather than leaving as an accident.

## The gate ran (2026-09-08)

`pyplan/gates/8.9a-wotlk-yulon-ubuntu-2026-09-08/`. All four definition-of-done
clauses PASSED live on yulon-ubuntu, plus the visible effect. Three restores of
the Hyper-V checkpoint `8.9a-purge-gate-2026-09-08b`; the box was handed back
with the stack up, both volumes and 1001 characters, verified rather than
assumed.

The deviation is recorded in that README rather than left to be noticed: the
gate line says "on a THROWAWAY install, never the finished 7.2 one" and this
used the finished one behind a checkpoint (owner's call, 2026-09-08). The
substitute protection is the rollback itself, and the README carries the
measurement that proves the rollback is real — files written after the
checkpoint were gone afterwards, while the three containers came back **Up**
rather than cold.

Two things this box could not settle, both because WotLK is a `fixed`-password
family:

* The **copy-and-recall** half of the blocker fix (copy written, folder deleted,
  reinstall reads the password back) is a `generated`-family path. `secret_kept`
  was `None` here, correctly. **8.9b owes that press.**
* "Characters on the login screen" was proved as its stated equivalent — the
  volume survived, `resolve_secrets()` still answers after the folder is gone,
  and 1001 character rows and 105 accounts were read through a fresh
  `mysql:8.4` on the kept volume. The last hop, a rebuilt server drawing the
  list on a real login screen, needs a full reinstall and is owed on 8.9b.
